# PRD: Octo 对话框支持自由调整高度

- Issue: #3
- 类型: Feature
- 优先级: P2
- 状态: PRD reviewed / accepted
- 来源: Octo 群反馈
- 反馈人: 檀小青
- PRD Owner: 小塔
- 日期: 2026-09-07

## 1. 背景

用户在 Octo 网页端对话框中编辑较长内容时，当前输入区域高度固定。长文本、长提示词、多段需求描述会堆积在较小的编辑空间内，导致用户需要频繁滚动输入框，难以同时查看正在编辑的上下文，影响输入效率和内容核对。

## 2. 目标用户

- 在 Octo 网页端输入长文本、长提示词、长需求描述或多段消息的用户。
- 需要边编辑边对照前后文的用户。
- 经常使用 Octo 进行需求讨论、Bug 反馈、Agent 指令编写的用户。

## 3. 用户问题

当前对话框编辑区域不能自由调整高度。用户输入大段文字时，可视编辑区域不足，前后文对照困难，容易漏改、重复滚动或误发送未检查完整的内容。

## 4. 目标

让用户在 Octo 网页端编辑长文本时，可以更灵活地扩大输入区域，减少输入框内滚动和上下文丢失，提高长内容编辑体验。

## 5. 非目标

- 不限定具体技术实现方式。
- 不涉及移动端输入框改造，除非后续确认移动端也存在同类需求。
- 不涉及富文本编辑器整体重构。
- 不改变消息发送、换行、附件、工具入口等既有核心操作语义。
- 不要求本次支持多窗口编辑、独立草稿页或全屏编辑器。

## 6. 用户故事

### 6.1 长文本编辑

作为 Octo 网页端用户，当我正在输入一段较长文字时，我希望可以把对话框编辑区域调高，以便一次看到更多正在编辑的内容。

### 6.2 对照前后文

作为需要整理需求或编写 Agent 指令的用户，当我修改一段多段落文字时，我希望输入区域能容纳更多上下文，减少反复滚动。

### 6.3 保持常用操作可用

作为高频用户，当我调整输入区域高度后，我仍然希望发送、换行、附件/工具入口等常用操作保持可见或易访问。

## 7. 功能范围

### 7.1 必须支持

- 网页端对话框编辑区域支持用户手动调整高度。
- 调整后，同一输入框内可展示更多正在编辑的内容。
- 调整过程中和调整后，发送、换行、附件/工具入口等常用操作仍可正常使用。
- 调整高度不应遮挡或破坏主要会话内容的基本阅读能力。
- 重新进入默认状态时，应有清晰、可预期的高度表现。

### 7.2 建议支持

- 设置合理的最小高度，避免输入框被缩到无法编辑。
- 设置合理的最大高度，避免输入框占满页面导致会话内容完全不可读。
- 支持恢复默认高度的方式，避免用户误操作后无法回到常用布局。

### 7.3 待产品确认

- 高度调整是否需要记忆：
  - 不记忆，每次进入恢复默认；
  - 记忆到当前会话；
  - 记忆到当前浏览器/当前用户。
- 交互方式优先级：
  - 手动拖拽；
  - 随内容自动增高；
  - 手动拖拽 + 自动增高。
- 是否只覆盖网页端，还是需要为移动端另开需求。

## 8. 验收标准

1. 用户在 Octo 网页端输入较长文本时，可以把对话框编辑区域调高。
2. 调整高度后，用户能在同一输入框内看到更多正在编辑的内容。
3. 调整高度后，发送、换行、附件/工具入口等常用操作仍可正常使用。
4. 输入框高度有合理上下限，不会小到不可编辑，也不会大到完全破坏会话阅读。
5. 用户误调整后，可以通过明确方式恢复到默认可用状态，或重新进入页面后回到默认高度。
6. 该能力不影响短消息输入体验；默认输入状态与当前习惯保持一致或变化可接受。

## 9. 风险与关注点

- 如果最大高度过大，可能遮挡会话历史，影响阅读。
- 如果高度记忆策略不清晰，用户可能认为布局异常。
- 如果只支持拖拽但入口不明显，用户可能不知道可以调整。
- 如果自动增高过于激进，可能打断当前会话阅读节奏。

## 10. Review 问题

请 reviewer 确认：

1. 本需求是否只覆盖网页端？
2. 高度调整是否需要记忆？如果需要，记忆范围是什么？
3. 首版更推荐“手动拖拽”还是“随内容自动增高”？
4. 是否需要把“恢复默认高度”列为首版必需能力？
5. 当前 P2 优先级是否合适？
